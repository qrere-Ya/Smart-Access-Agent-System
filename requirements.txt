# ==========================================
# Smart_Access_Agent_System 合併專案 - 統一依賴套件清單
# 這份檔案合併了原本 Edge_LlamaIndex_RAG 與 My_Smart_Access_System 各自的
# requirements.txt。標準安裝方式（兩個步驟，順序不能反）：
#   1) pip install -r requirements.txt
#   2) pip install retinaface --no-deps      ← 一定要加 --no-deps，見下方說明
#
# ✅ Python 3.10 相容性：已用 PyPI 的套件中繼資料逐一核對（2026-09-01），這份
#    清單裡列出的每一個套件版本都明確支援 Python 3.10，且都有對應的 Windows
#    cp310 wheel（opencv-python 用的是涵蓋 3.10 的 abi3 通用 wheel），可以放心
#    在 Python 3.10.0 的環境下安裝，不會有「這個版本根本不支援 3.10」的問題。
#
# ⚠️ 版本衝突說明（我沒辦法在你的電腦上實測，請安裝完務必自己跑一次驗證）：
#   - numpy：RAG 端原本鎖 1.26.4（註解說是為了相容性），門禁系統端是 2.2.6。
#     兩個沒辦法同時滿足，這裡選擇門禁系統的 2.2.6（比較新，AI 視覺那邊的套件
#     對版本比較敏感）。經查 tensorflow==2.21.0、onnxruntime==1.23.2、
#     ultralytics==8.4.159、scikit-image==0.25.2 這幾個對 numpy 版本最敏感的套件，
#     官方相依需求都是「numpy>=1.x」沒有設上限，所以 numpy 2.2.6 不會在安裝階段
#     衝突。但這不保證程式「執行時」不會因為 numpy 2.x 的行為變化而出錯，
#     如果之後 llama-index / faiss-cpu / huggingface-embeddings 在 numpy 2.x 下
#     報錯，代表這個相容性問題還沒解決，需要另外處理（例如把 RAG 部分改到獨立的
#     虛擬環境跑）。
#   - torch：RAG 端原本是 2.3.0，門禁系統端是 2.12.0，這裡選擇比較新的 2.12.0。
#
# 🚨 retinaface 必須「另外」安裝，不能放在上面這行一起裝（重要，會影響 tensorflow）：
#    retinaface==1.1.1 這個套件自己在 PyPI 上宣告寫死要裝 tensorflow==2.5.0（一個
#    2021 年的極舊版本，甚至不支援 Python 3.10！），如果照一般方式跟其他套件一起
#    `pip install -r requirements.txt`，pip 的相依解析器會試圖把我們要的
#    tensorflow==2.21.0 換成這個舊版，直接打壞整個視覺辨識環境，或是解析失敗直接
#    報錯裝不成功。這正是你自己 GitHub README 裡特別提醒的安裝注意事項。
#    解法：requirements.txt 完全不列 retinaface，永遠用下面這行「單獨、額外」安裝：
#        pip install retinaface --no-deps
#    --no-deps 的意思是「只裝 retinaface 這個套件本身，不要理會它宣告的相依套件」，
#    因為我們要的 tensorflow / opencv 版本已經在上面裝好了，retinaface 實際執行
#    不需要真的用到 2.5.0 版的 tensorflow。
#
# 🎮 GPU / CPU 二選一（onnxruntime）：
#    下面預設列的是 onnxruntime==1.23.2（CPU 版）。如果你的電腦有 NVIDIA 顯卡且已
#    裝好對應版本的 CUDA Toolkit + cuDNN，可以改成：
#        onnxruntime-gpu==1.23.2
#    兩個套件功能重疊、不要同時裝，否則兩邊的 onnxruntime 動態庫會互相打架。
#
# 🚨 litellm 最後結論：還是要裝在「獨立的虛擬環境」，但原因跟之前不一樣了
#    （2026-09-01 兩次更新，這是最新、最終的結論）：
#
#    第一次更新時我以為只要把 llama-index 升級到 0.14.x（見下方版本，讓
#    llama-index-llms-openai 放寬到允許 openai <3,>=1.108.1），跟 litellm 要求的
#    openai >=2.20.0,<3.0 就有交集了，可以裝同一個環境。這個版本號的推理沒有錯，
#    但實際讓你去裝、去跑 `litellm --config config.yaml` 之後，發現一個更根本的
#    問題：litellm 從 1.85.0 到目前最新的 1.99.0，程式碼裡有好幾個地方直接寫
#    `from typing import NotRequired`——但 `NotRequired` 這個東西是 Python 3.11
#    才加進標準函式庫的（PEP 655），Python 3.10（你電腦用的版本）根本沒有這個東西，
#    所以只要載入 litellm 就會直接 ImportError，跟版本號怎麼配都沒關係，是
#    litellm 自己程式碼對 Python 3.10 支援不完整的問題（雖然它在 PyPI 上寫的是
#    支援 >=3.10）。我實際下載了 1.80.0 到 1.99.0 之間好幾個版本的原始碼逐一核對
#    過，確認這個 bug 從 1.85.0（litellm 開始要求 openai>=2.20 的那個版本）就已經
#    存在，一路延續到最新版，沒有一個「同時滿足 openai>=2.20 又不踩到這個 bug」的
#    litellm 版本。
#
#    真正乾淨的解法：litellm 用「另一個 Python 3.11 以上版本」的直譯器建立獨立虛擬
#    環境來跑（不是 Python 版本不同就一定要分開環境，是這次剛好 litellm 本身的
#    程式碼假設了 3.11+，用回 3.11+ 直譯器就完全沒有這個問題）。詳細安裝指令見
#    README.md 的「🚀 啟動方式」那一節。這個虛擬環境跟這份 requirements.txt 安裝的
#    主環境（維持 Python 3.10.0，因為門禁系統的人臉辨識/視覺套件是針對 3.10 測試
#    的）完全分開、不衝突。
# ==========================================
