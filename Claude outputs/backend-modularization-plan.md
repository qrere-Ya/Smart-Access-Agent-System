# 後端模組化重構方案：參考 Syscom Cubi 的「功能模組組」設計

參考來源：你附的 4 張 Syscom Cubi 截圖（功能模組卡片式 launcher、即時系統效能、AI 用量與成本透明化、嚴謹權限控管、帳號管理、與既有系統整合）。

**前提說明**：這份方案不是要複製 Cubi 的功能（企業內控、多租戶計費、公文系統整合這些超出畢業專題範疇），而是借用它的**組織方式**——用「功能模組卡片」取代現在一整排按鈕塞在同一支程式裡的做法，並且盡量用你現有的程式邏輯去填，不整包重寫。

---

## 一、先把 Cubi 截圖拆解成「設計語言」，而不是「功能清單」

截圖裡真正值得借用的，是這 4 個組織原則，跟畫面上具體長什麼樣子無關：

1. **首頁是「模組啟動器」，不是「功能全部攤開」**：7 個卡片（Cubi CHAT / RAG / AI / Note / ADVISOR / TOUR / AGENT），每張卡片點進去才是那個功能自己的畫面。你現在的 `backend_main.py` 是反過來——所有功能的按鈕、狀態、console 全部攤在同一個視窗裡。
2. **系統本身有「自我監控」的意識**：即時 CPU/RAM、時鐘。你的 `backend_main.py` 已經有 `refresh_dashboard_data()`（每 5 秒讀資料庫算今日到職/異常），概念上已經是「自我監控」，只是還沒把系統資源（CPU/RAM）也一起顯示。
3. **AI 的行為要「可被看見、可被稽核」**：用量儀表板、對話紀錄符合法規稽核。你目前完全沒有這塊——RAG 助理回答了什麼、guardrail 攔截了什麼問題、SQL 路由判斷對不對，這些事件目前**跑完就消失**，沒有留下任何紀錄。
4. **權限是「誰能用什麼」的矩陣，不是有跟沒有**：哪些人能查哪些資料、哪些操作要審核。你現在的 `Users` 表沒有角色欄位，RAG 的 SQL 引擎雖然已經刻意排除人臉特徵欄位（這點做得對），但沒有「這個問題是誰問的、他有沒有資格問」這一層。

對應下來，你現有系統跟 Cubi 的落差主要不是「功能少」，而是「這些概念散落在各處、沒有被組織成使用者看得懂的模組」。這正好是一個很適合放進畢業專題的**架構升級**，而不是要新做一堆沒做過的東西。

## 三、兩條可行路線（這是你要做的第一個決定）

### 路線 A：維持 Tkinter，改成「卡片式 launcher」（風險低、改動小）

把 `backend_main.py` 現在那一排按鈕，改成用 `tkinter.Grid` 排成卡片牆，每張卡片對應一個既有功能（門禁監控 / RAG 問答 / 帳號管理 / 用量儀表板 / QR 註冊），點下去才切換到該功能的畫面或開啟對應視窗。

- 優點：完全延續現有架構，不用重新設計啟停/port 檢查那套已經穩定運作的機制，風險最低。
- 缺點：Tkinter 卡片視覺質感天花板有限，很難做到截圖裡那種漸層卡片、圓角陰影的精緻度；而且展示畢業專題時，Tkinter 視窗只能在你自己電腦上開，不方便截圖或給口試委員遠端看。

### 路線 B：把「戰情主控台」從 Tkinter 遷移到 Web（你已經有 `web_server.py` 的 Flask 基礎）

新增一個 Flask 路由（或獨立擴充 `web_server.py`），做一個瀏覽器版的管理儀表板：卡片式模組 launcher、即時系統效能（透過 WebSocket 或輪詢 API）、帳號管理表格、用量儀表板，視覺上可以直接照抄截圖的排版邏輯（Tailwind/CSS 即可，不需要額外框架）。`backend_main.py` retained 只負責「啟動這些服務、在背景常駐」，管理介面全部搬到瀏覽器。

- 優點：視覺質感可以真正接近截圖水準；瀏覽器版天生適合口試展示（投影、遠端都能看）；跟你手機掃 QR 註冊的體驗一致（同一套 Web 技術棧）。
- 缺點：改動範圍比路線 A 大，等於是新增一整層 Web 管理介面，`backend_main.py` 原本「戰情室」的角色要重新定位成「背景服務啟動器」，需要多一點工程量，且要重新測試部署路徑（防火牆、port）。

**我的建議：路線 B。** 理由：這個專題最終是要口試展示的，瀏覽器版的模組化管理介面，展示效果、跟截圖的相似度、以及未來要不要放上你的作品集網站，都比 Tkinter 視窗更有利；而且你已經有 Flask 基礎（`web_server.py`），不是從零開始。但這是工程量的取捨，最終還是要你決定——如果時程比較緊，路線 A 也完全站得住腳，一樣能達到「模組化」的效果。

## 四、具體重構步驟（不管選 A 或 B，前兩步都一樣）

### 🔴 P0：新增 AI 用量與決策紀錄表（風險極低，且直接對應你之前問的「學術性功能」）

新增一張 `llm_usage_log` 表（`database.db` 裡），欄位大致是：`id, timestamp, question, route(law/attendance), guardrail_pass(bool), similarity_score, is_pass(供evaluate_rag.py用), source(gradio/eval)`。

在 `rag_guardrail.py` 的 `check_semantic_guardrail()` / `check_query_route()`，以及 `main_guardrail_rag.py` 的 `get_chat_response()` 這幾個既有函式**最後**加一行寫入紀錄，不改動任何判斷邏輯本身，純增量、不影響現有行為，風險接近零。

這一步的價值是一魚兩吃：一是 Cubi 截圖裡「AI 用量與成本透明化」的資料基礎，之後隨時可以做成一個小圖表；二是直接餵給你之前 `academic-enhancement-plan.md` 裡「方向5：RAG 評估樣本擴充」——有了持續累積的真實使用紀錄，你的評估就不再只是手動跑 `evaluate_rag.py` 的抽樣題目，而能報告「系統上線 X 週以來，guardrail 攔截率 / 路由正確率的實際趨勢」，這是口試時很有說服力的量化數據。

### 🟠 P1：完成 `backend_main.py` 的 God Class 拆分（這本來就排在健檢報告的 P2，現在有了明確的模組邊界）

health check 報告原本只說「拆成幾個類別」，比較抽象；現在可以直接照 Cubi 的模組概念拆：

```
backend_main.py          — 輕量殼層，只做視窗骨架 + 模組卡片點擊分派
service_manager.py       — 三個子程式（RAG/人臉辨識/QR註冊）的啟停、port 檢查（原本散在 966 行裡的邏輯搬出來）
dashboard_stats.py       — 業務數字（今日到職/異常）+ 新增系統資源（CPU/RAM，用 psutil）
console_panel.py         — console 顯示元件
account_admin.py         — 帳號管理 CRUD（新功能，見 P2）
```

這步是把「健檢報告本來就建議做的重構」跟「這次的模組化目標」合併成同一次工程，不用做兩次。

### 🟡 P2：帳號管理模組（新功能，順便解決重複註冊的歷史包袱）

`Users` 表加一個 `role TEXT DEFAULT 'employee'` 欄位，`account_admin.py`（或路線 B 的話是一個網頁表格）做一個可以「列出所有員工、標記/停用、刪除」的介面——這同時也是清掉資料庫裡 5 筆重複「陳柏豫」測試資料最乾淨的方式（比我之前直接下 SQL 指令風險低，因為有介面可以先看清楚再刪）。

### 🟢 P3：模組卡片 launcher（視覺層，路線 A/B 由此分岔）

把 P1 拆出來的各模組，用卡片方式排版呈現，仿造截圖的排版邏輯（一排 4-5 張卡片、每張卡片一個圖示＋名稱＋簡短說明）。

### 🟢 P4（選配，時間夠再做）：Cubi ADVISOR 概念——異常事件主動觸發法規提醒

`integration-analysis.md` 裡本來就提過的「選配」功能：門禁偵測到連續遲到/尾隨警報時，自動丟一個問題給 RAG 助理，把回答顯示在儀表板上。有了 P0 的用量紀錄表之後，這個功能產生的呼叫也會自動被記錄下來，不用另外處理。

## 五、不建議做的部分（避免範疇蔓延）

- Cubi Note（企業筆記協作）、Cubi TOUR（產品導覽教學）：跟門禁+RAG 的核心主軸無關，做了也很難在口試裡講出「為什麼需要」。
- 「與既有系統整合」（HR/公文/財務系統）：截圖裡這塊是給真正企業客戶用的，你的專題沒有這些外部系統可接，做了也只是空殼 API，建議完全跳過，最多在文件裡寫「架構上預留擴充可能性」帶過一句就好。
- 多租戶計費/依模型分開計費：你的 RAG 是本地 Ollama，沒有真正的 API 計費問題，這塊做了也沒有意義。

## 六、決定順序建議

1. 先決定路線 A（Tkinter 卡片）還是路線 B（遷移到 Web 管理介面）——這決定 P3 要怎麼做，但不影響 P0/P1/P2。
2. P0（用量紀錄表）可以現在就開始動手，跟路線 A/B 的決定無關，而且對你之前的學術性加強計畫直接有幫助，建議最優先做。
3. P1（God Class 拆分）本來就是健檢報告排定要做的事，這次只是把邊界訂得更清楚，可以接著 P0 之後做。
4. P2、P3 等前面穩定之後再排。
