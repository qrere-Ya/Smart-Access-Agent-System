# P2 修改報告：帳號管理模組

## 做了什麼

1. **`database_mgr.py`**：`Users` 表新增兩個欄位——`role TEXT DEFAULT 'employee'`、`is_active INTEGER DEFAULT 1`。因為你電腦上的資料庫已經有資料，`CREATE TABLE IF NOT EXISTS` 不會幫已存在的表補新欄位，所以我在 `init_db()` 裡加了一段用 `PRAGMA table_info` 檢查欄位存不存在、不存在才 `ALTER TABLE` 補上的升級邏輯——不管是全新安裝還是你現在這個已經有 7 筆員工資料的舊資料庫，都能正確升級，既有資料的 `role` 會是 `'employee'`、`is_active` 會是 `1`（啟用），不會意外把任何人變成停用。

2. **`recognize_face()` 改了查詢條件**，只拿 `is_active=1` 的員工特徵去做 1:N 比對。這是必要的修改：停用一個帳號要真的有效果（刷臉變成查無資料），不能只是管理畫面上打個叉好看而已。

3. **新增 `account_admin.py`**（87 行）：`list_users()` 列出所有員工（含角色、啟用狀態、最新打卡狀態）、`set_active()` 停用/啟用、`delete_user()` 刪除。刪除只動 `Users` 表，不會動 `Attendance` 打卡歷史（打卡紀錄用姓名字串記錄，不是關聯 `Users.id`，帳號刪掉了，這個人過去的打卡歷史還是完整保留，只是之後沒辦法再刷臉打卡）。

4. **`backend_main.py`**：原本「📇 員工資料庫管理」那個唯讀視窗，升級成「👤 員工帳號管理」——列表多了角色/狀態欄位，下面新增四顆按鈕：🔄 重新整理、⏸️ 停用所選、▶️ 啟用所選、🗑️ 刪除所選（可以一次選多筆）。刪除會先跳確認視窗列出要刪除的姓名，按「否」就什麼都不會發生。

## 關於清掉 5 筆重複陳柏豫

我**沒有**直接從這裡改你電腦上的 `database.db`。理由：資料庫檔案跟原始碼不一樣，它是「活的」——你的 app 隨時可能在寫入新的打卡紀錄，如果我在這裡下載一份快照、改完再整份寫回去，萬一你這段時間真的有人刷卡，那筆紀錄就會被我的舊快照覆蓋掉。這也是之前那次我幫你插入測試行事曆資料、遇到 `disk I/O error` 的同一個風險，這次不想再冒一次。

比較安全的做法：新的「👤 員工帳號管理」介面已經測過可以正常運作，麻煩你自己在電腦上打開它，勾選 5 筆陳柏豫裡的其中 4 筆，按「🗑️ 刪除所選」。我的建議是**留下最後註冊的那一筆（清單裡 id 最大的那筆，通常排在最下面）**，因為那筆的人臉特徵最可能是最近拍的、最準；其他 4 筆刪掉哪些都一樣安全——不管留哪一筆，「陳柏豫」的打卡歷史都不會受影響（原因見上面第 4 點）。

## 怎麼驗證的

跟前兩次一樣分層測試，這次特別針對你的真實情境（5 筆重複陳柏豫）做了端到端模擬：

- 手動建立一個「舊版 schema」的假資料庫（沒有 role/is_active 欄位，7 筆使用者、5 筆重複陳柏豫，模擬你電腦上現在的真實狀態），呼叫 `init_db()` 後確認欄位正確補上、既有資料完全沒被動到。
- `account_admin.list_users()` 正確列出全部使用者、正確附上最新打卡狀態；資料庫打不開時安全回傳空清單，不拋例外。
- 直接驗證「停用」真的讓 `recognize_face()` 比對不到那個人（回傳 Unknown），重新啟用後又能比對到，證明停用不是好看的假按鈕。
- 模擬真正的清理流程：刪除 4 筆重複陳柏豫（id 1~4，保留 id 5），確認剩下 1 筆、且 `Attendance` 打卡歷史完全沒被動到。
- 用打樁的 Tkinter/ttkbootstrap 元件把整個「員工帳號管理」視窗跑過一遍：開視窗 → 確認表格列出 6 筆（5 陳柏豫 + 1 葉君緯）→ 沒選取就按停用（正確跳出提示，沒誤操作）→ 選 1 筆停用 → 確認表格顯示「已停用」→ 啟用 → 選 4 筆按刪除、按「否」（確認真的沒刪）→ 再按「是」（確認表格正確刷新成剩 2 筆）→ 重新整理。全部通過。
- 額外重跑了 P1 那一輪的完整回歸測試（戰情儀表板、人臉辨識開關、AI 代理設定、RAG 啟動、QR 註冊），確認這次改動沒有動到其他視窗的行為。

所有檔案都用你原始檔案的修改時間當版本鎖寫回你的電腦，確認沒有覆蓋掉你電腦上更新過的版本。
