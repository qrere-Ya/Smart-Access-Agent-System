# Smart Access Agent System 專案現況

### 門禁人臉辨識 + 勞基法 RAG 助理

更新日期：2026-09-09

---

## 一、專案是什麼

這個專案其實是兩個系統合併成的一個資料夾：

- **`My_Smart_Access_System`（門禁系統，「身體」）**：攝影機即時人臉辨識 → 活體偵測（防止拿照片矇騙）→ 自動打卡（上班/遲到/早退/下班）→ YOLOv8 防尾隨偵測 → 語音播報 → 手機 QR Code 掃碼註冊。
- **`Edge_LlamaIndex_RAG`（RAG 助理，「大腦」）**：本地端 LLM（Qwen2-7B via Ollama）驅動的問答系統，專門回答勞基法規定跟即時考勤查詢，有語意防護欄擋掉無關問題，也有一套自動化評估系統（出題官／考生／裁判官三角色互測）。

兩邊透過同一個 SQLite 資料庫（`database/database.db`）串接：門禁系統負責寫入打卡紀錄，RAG 系統即時查詢這份資料回答問題，不是靠靜態 CSV。

技術棧：RetinaFace + ArcFace（人臉辨識）、MiniFASNetV2（活體偵測）、YOLOv8（防尾隨）、ONNX Runtime（推論）、FAISS + BGE-M3（RAG 向量檢索）、LiteLLM Proxy（把出題官／裁判官接到 NVIDIA Gemma API）。

程式碼跑在兩台實體電腦：桌機（`E:\py_code\Smart_Access_Agent_System`，開發用）跟筆電（`C:\Users\qrere\Downloads\Smart_Access_Agent_System`，有攝影機，實測用），目前是手動同步，還沒有自動化。

## 二、已完成並在真實硬體上驗證過

### 門禁系統 / 基礎架構
- 拒絕重複註冊（同姓名或同員編直接擋下，不寫入資料庫）——手機實測確認。
- QR 註冊視窗啟動時安靜等待，不再狂印錯誤堆疊。
- 人臉辨識啟動崩潰修正（numpy 相容性問題：`np.bool` 猴子補丁誤蓋掉新版 numpy 自己的型別）。
- WiFi-Direct 熱點的 IP 自動偵測（`get_local_ip_offline()`），手機實測路由器 IP 跟 App 顯示網址完全一致。
- 打卡時播報行事曆：改用 Windows 上能正常運作的 `audio_player`，不再依賴會靜默失敗的 Linux-only 播放方式。
- 字型快取（`put_chinese_text()`）：這次直接對部署中的程式碼做基準測試，1400 次模擬呼叫只觸發 2 次真正的硬碟讀取，效能改善確認為真。
- 常駐分析 worker + Queue 取代每幀重新開執行緒，共用資料加上 Lock。

### RAG 系統
- SQL 回答「只有人數沒有姓名」時句子斷在冒號後面——修好。
- 簡短追問（「有名子嗎?」）被防護欄誤擋——加上「上一句對話」當上下文，修好。
- `main_guardrail_rag.py`（原本 700+ 行、身兼六個角色）拆成 4 個子模組 + 1 個統籌檔案，用真實 Ollama 重新驗證答案一致。
- 自動評估系統的出題官／裁判官模型別名 bug（本地套件不認得自訂別名）——改用 `gpt-4o` 別名解決。
- **考勤路由關鍵字快速通道**：像「周宇祥」這種語意分類偶爾不穩定的人名，加上「打卡時間」「系統判定狀態」等關鍵字快速通道，直接判定考勤，跳過語意相似度計算。
- **考勤 SQL 確定性查詢**：原本依賴小模型自己翻譯 SQL，遇到「姓名+具體日期」問題常常只抓最新一筆、漏掉裁判官要的那一筆，改成程式碼直接查、不靠小模型翻譯，真實環境重測後純考勤類別從 0/3 提升到 3/3。
- **評估系統判分 bug**：裁判官輸出「合格」但沒有額外包一層方括號時，舊解析邏輯辨識不出來、誤判成不合格，導致畫面顯示合格但彙總報告卻不合格。已修正為直接比對中文詞本身，不要求方括號。
- 評估流程畫面重新設計：考生／出題官同一個對話視窗，靠角色（`role="assistant"` / `role="user"`）左右分邊，不再混在一起或另開視窗。
- **2026-09-09 重測結果，系統整體第一次拿到「✅ 合格」**：純法規 2/3、純考勤 3/3、正負例 6/6，綜合答題合格率 83.3%、幻覺率 0%、防護欄準確率 100%，三項門檻全部達標。

### WiFiDirectHotspotCore（自製熱點工具）
- `WiFiDirectAdvertisementPublisher` 成功在真實筆電上編譯、啟動、建立合法熱點，手機實測連得上，取代 MyPublicWiFi 的可行性已驗證。

## 三、程式碼已寫好，還在等你確認

- 常駐 worker 畫面流暢度：需要接攝影機實際跑一段時間，肉眼確認不卡頓、CPU 使用率下降——這項需要你在有攝影機的電腦上實測，無法遠端驗證。
- 打卡語音播報：目前資料庫裡的 `calendar` 表是空的，現有的 7 位員工都沒有「今日行程」測試資料，直接測不會聽到播報（不是功能壞掉，是沒有測試資料）。建議用手機新註冊一位測試員工來測（註冊會自動帶一筆假行程），比較不會有資料庫寫入衝突的風險。

## 五、已知、不算 bug 的限制

- 純法規評估裡偶爾出現的答錯，多半是本地 7B 模型（Qwen2-7B）對勞基法細節計算/期限規則不夠精準（例如漏乘加班小時數、搞混「離職生效日」跟「30 天給付期限」），不是檢索錯資料，也不是程式邏輯問題，程式碼修不了，只能靠換更大的模型或加強法規文件解說。
- 語意路由分類（`check_query_route()`）在少數邊界案例仍可能誤判，但既有的「查無資料就順便問問法規」fallback 機制通常能把答案救回來。
