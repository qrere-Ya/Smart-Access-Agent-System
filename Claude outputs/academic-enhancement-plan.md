# 專題學術性強化計畫

### Smart Access Agent System（門禁人臉辨識 + 勞基法 RAG 助理）

撰寫日期：2026-09-09

---

## 一、問題背景

目前專案在「系統整合」跟「工程實作」這兩塊已經有相當的完成度：門禁人臉辨識、防尾隨、即時考勤 RAG 問答、自動化評估框架（`evaluate_rag.py`）都已經在真實硬體上驗證過，也修過不少實際遇到的 bug（考勤路由誤判、SQL 查詢邏輯、numpy 相容性問題等，完整紀錄見 `claude/implementation-log.md`）。

但目前的成果比較偏「做出一個能動的系統」，缺少大學專題通常要求的「有系統的實驗設計」跟「量化評估」——也就是不只是「它能動」，還要能回答「它做得好不好、好在哪裡、為什麼這樣設計比別的設計好」這類問題，並且用數據支撐答案。

好消息是：`evaluate_rag.py` 那套「出題官／考生／裁判官」的 LLM-as-a-Judge 評估框架，加上已經在用的「矛盾／遺漏關鍵資訊／幻覺瞎掰」三分類錯誤分析法，其實已經是論文評估章節的雛形——現在只是拿它來 debug，還沒有系統性地拿來做比較實驗。這份計畫就是要把現有的工程成果，往學術評估的方向補齊。

---

## 二、五個強化方向

### 方向 1：RAG 系統的消融實驗（Ablation Study）

**現況**：`evaluate_rag.py` 目前只拿來測「系統整體表現」，沒有拆解每個機制各自的貢獻。

**具體做法**：用同一批題目，系統性地開關以下機制，各跑一次評估，比較數字差異：

- 有無 `LongContextReorder`（解決 LLM 的 Lost-in-the-Middle 問題）
- 對比式語意防護欄（Contrastive Semantic Guardrail）vs. 單純關鍵字過濾
- 考勤路由：關鍵字快速通道 + 語意分類 vs. 純語意分類（這次除錯過程剛好留下了「周宇祥被誤判成法規」這個真實案例，可以直接寫進論文當作動機）
- 確定性 SQL 查詢 vs. 讓小模型自己翻譯 SQL（這次也是真實踩過的坑：小模型翻出來的 SQL 常常只抓最新一筆，跟確定性查詢比較起來準確率差異很大，已經有真實數據可以用）

**成本**：低。框架已經存在，只需要寫幾組「開關某個機制」的設定，重跑評估即可。

**產出**：一張比較表（各機制開/關時的答題合格率、檢索命中率、幻覺率），可以直接放進論文的實驗章節。

---

### 方向 2：人臉辨識的量化評估（FAR / FRR）—— 目前最大的學術缺口

**現況**：系統用歐氏距離門檻 `1.0` 判斷是否為同一人（`recognize_face()`），但這個門檻是憑經驗設定的，完全沒有系統性測過「這個值選得對不對」。

**具體做法**：這是生物辨識系統論文的標準評估方法：

1. 蒐集一批測試用的人臉樣本（例如找 10-15 位同學，每人拍攝多張不同角度/光線的照片），比現有 7 位員工的樣本量大很多。
2. 在不同的距離門檻下（例如 0.6、0.8、1.0、1.2、1.4...），分別計算：
   - **FAR（False Acceptance Rate，誤接受率）**：不同的兩個人被誤判成同一人的比例
   - **FRR（False Rejection Rate，誤拒絕率）**：同一個人被誤判成不同人的比例
3. 畫出 ROC 曲線或 DET 曲線，找出兩條曲線的交叉點（等錯誤率 EER），回頭驗證目前選的 `1.0` 是否接近最佳門檻。

**成本**：中等。需要額外蒐集測試資料（這是主要工作量），計算跟畫圖的程式碼不複雜。

**產出**：ROC/DET 曲線圖 + EER 數值，這是整個專案裡學術含金量最高、也是評審最容易一眼看懂「有做實驗」的部分。

---

### 方向 3：活體偵測（Liveness Detection）準確率量化

**現況**：`vision_core.py` 已經用 `MiniFASNetV2` 做活體偵測（防止拿照片/影片作弊），但沒有測過實際的防禦成功率。

**具體做法**：
- 蒐集一批「真人」樣本 vs. 一批「用手機/平板播放照片或影片冒充」的樣本
- 實際跑一次活體偵測，統計正確攔截偽造攻擊的比例（類似上面的 accuracy／precision／recall）

**成本**：低～中。不需要額外訓練模型，只需要蒐集測試樣本並實際跑一次分類統計。

**產出**：一個簡單的混淆矩陣（真人/偽造 × 判定通過/判定攔截），加上準確率數字。

---

### 方向 4：邊緣運算效能實測（ONNX Runtime 選型的實證支撐）

**現況**：`architecture.md` 裡已經寫了「選擇 ONNX Runtime 而非 PyTorch/TensorFlow」的理由（推論速度快、部署輕量），但目前是敘述性的說明，沒有實測數字支撐。

**具體做法**：
- 實測目前系統在你的硬體上，人臉偵測 → 對齊 → 特徵萃取這條 pipeline 的實際推論延遲（毫秒）與整體 FPS
- 如果時間允許，額外跑一次「同一個模型用 PyTorch/TensorFlow 原生推論」當對照組，實測延遲差異，直接驗證「為什麼選 ONNX」這個設計決策

**成本**：低。只是加計時碼跟統計，PyTorch/TensorFlow 對照組如果時間不夠可以省略，單純報告目前系統的延遲數字也足夠當作系統效能章節的素材。

**產出**：一張效能表（各階段推論延遲、整體 FPS），把原本「敘述性理由」升級成「有數據支持的設計決策」。

---

### 方向 5：RAG 評估的樣本數與指標擴充

**現況**：目前每類別只抽樣 3 題，樣本數太小，任何百分比數字在統計上都禁不起檢驗（答辯時容易被問「這個數字有意義嗎、樣本夠嗎」）。檢索品質也只有「命中率」一個指標。

**具體做法**：
- 把 `questions_per_category` 從 3 提高到 20~30，讓百分比數字更站得住腳
- 除了現有的檢索命中率，可以加上 Precision@k（top-k 檢索結果裡有幾個真的相關）

**成本**：低，改一個參數＋重跑評估即可（實際跑的時間會變長，因為要呼叫更多次 API/本地模型）。

**產出**：更有統計意義的評估數字，可以附上信賴區間或至少講清楚樣本數。

## 三、建議優先順序

| 優先度 | 項目 | 理由 |
|---|---|---|
| 1 | 方向 5：擴大評估樣本數 | 成本最低（改參數即可），立刻讓現有數字更有說服力 |
| 2 | 方向 1：RAG 消融實驗 | 框架已經現成，且已經有真實踩坑案例（路由誤判、SQL bug）可以直接當實驗動機 |
| 3 | 方向 4：邊緣運算效能實測 | 成本低，補齊 architecture.md 裡已經寫的設計決策 |
| 4 | 方向 3：活體偵測準確率 | 中等成本，需要額外蒐集偽造樣本 |
| 5 | 方向 2：人臉辨識 FAR/FRR | 學術含金量最高，但需要額外蒐集較大量的人臉測試資料，工作量最大，建議留最多時間 |
