# RAG 考勤查詢：SQL 使用方式確認報告

你問的是：AI 是不是真的用標準資料庫語言（`SELECT ... FROM ... WHERE ... ORDER BY ...`）去查資料庫、把結果丟回去給 AI 確認、再回答使用者。

答案：**是，現有程式碼本來就是這樣做的，這部分已經完成，不用再另外開發。** 下面附實際程式碼佐證，分兩條路線說明。

## 路線一：姓名＋日期的確定性查詢（`rag_sql_engine.py` 的 `_try_deterministic_date_lookup`）

當問題裡同時出現「真實存在的員工姓名」跟「YYYY-MM-DD 格式的日期」，系統不讓小模型自己翻譯 SQL，而是直接執行寫死、保證正確的參數化查詢：

```python
SELECT timestamp, status FROM Attendance
WHERE name = ? AND timestamp LIKE ?
ORDER BY timestamp ASC
```

`ORDER BY` 用的是升冪，會把那個人那一天「全部」的打卡紀錄依時間排序列出來，不會只挑最新一筆——這是 2026-09-08（七度更新）修正過的地方，原本讓小模型自己翻譯常常只抓 `ORDER BY timestamp DESC LIMIT 1`（最新一筆），跟裁判官抽到的那一筆對不上，被誤判「矛盾」。這條路線刻意繞過小模型，用真人寫死的 SQL 保證正確。

## 路線二：其他問題交給 `NLSQLTableQueryEngine`（llama_index）翻譯真正的 SQL

不符合「姓名＋日期」句型的問題（例如「目前員工有幾人」「有哪些員工」），交給本地小模型（qwen2:7b）依照 few-shot 範例翻譯成 SQL。提示詞 `_SQL_TEXT_TO_SQL_PROMPT_ZH` 明確要求輸出格式：

```
Question: 問題內容
SQLQuery: 要執行的 SQL 查詢語句
SQLResult: SQL 查詢語句的結果
Answer: 最終答案
```

並限制只能查兩個安全的資料庫物件：
- `EmployeeRoster`（員工名冊類問題）——這是一個**特意建立的 SQL VIEW**，結構上就不包含人臉辨識用的 512 維 `embedding` 生物特徵欄位，不是靠提示詞「拜託不要查」，是資料庫層級直接讓那個欄位不存在於這個 VIEW 裡。
- `Attendance`（打卡／出缺勤類問題）。

而且執行查詢用的資料庫連線是**唯讀**（`?mode=ro` URI 開啟），就算小模型不小心翻譯出奇怪或想修改資料的 SQL，實體資料庫也不可能被寫入或竄改。

## 查詢結果怎麼「回傳給 AI 確認」

不管走哪條路線，實際查回來的 SQL 結果都會被塞進另一個提示詞 `_SQL_RESPONSE_PROMPT_ZH`，交給 LLM 組成最終的繁體中文回答，這一段就是你問的「回傳給ai確認 並回答使用者答案」：

```
問題: {query_str}
SQL 查詢語句: {sql_query}
SQL 查詢結果: {context_str}
回答規則：
1. 只根據 SQL 查詢結果回答，不要自己瞎猜或補充查詢結果以外的資訊。
2. 如果 SQL 查詢結果是空的或 0 筆，請直接誠實回答「查無符合條件的資料」...
```

換句話說：AI 不是憑印象亂答，是先看到「這句話真正查出來的資料」才組答案，而且明文禁止它在資料之外自己腦補。

## 有沒有「真的查到東西」的判斷方式

`try_attendance_answer()` 判斷成功與否，用的是 SQL 實際回傳的**原始資料列數**（`sql_response.metadata['result']`），不是拿 AI 回答的文字去比對「查無資料」這幾個字——因為 AI 换句話說的方式很多種，字串比對不可靠，用查詢引擎回傳的原始資料列數判斷才不會出錯。這點在你先前確認的 P2 帳號管理報告也用了同樣的設計精神（判斷「真的做了什麼」看系統實際狀態，不是看訊息文字）。

## 完整流程：從「這句話該不該答」到「查哪裡」到「回答」

補充你可能也想知道的上下游（`rag_guardrail.py` + `main_guardrail_rag.py`）：

1. **`check_semantic_guardrail()`**：先判斷這句話是不是在問人事差勤/法規範圍內的事，語意相似度算出來太低或偏向「無關」就直接攔截，不會進到 SQL 這一步。
2. **`check_query_route()`**：通過防護欄後，再判斷該查「即時考勤資料庫」還是「勞基法規向量索引」——含一個關鍵字快速通道（例如句子裡出現「打卡時間」「打卡紀錄」直接判定考勤，不用等語意相似度算完）。
3. 判定是考勤類 → 呼叫上面兩條 SQL 路線；查無資料 → 自動改問法規那邊（雙向 fallback，避免「遲到扣薪合不合法」這種其實在問規則、卻被誤判成考勤的問題死在半路查無資料）。
4. 每一步（guardrail 放行/攔截、路由分類、SQL 查詢結果）都會寫進 P0 的 `llm_usage_log` 稽核紀錄表——這部分你在 9/12 前後已經確認完成。

## 結論

你擔心的「AI 是不是真的用資料庫語言查詢，還是憑印象亂講」，程式碼層面已經做到：兩條 SQL 路線都是貨真價實的 `SELECT/FROM/WHERE/ORDER BY`（一條寫死保證正確、一條由小模型依 schema 現場翻譯），且限制在安全的資料表/視圖範圍內、唯讀連線、查詢結果強制先給 LLM 看過才能組答案、禁止腦補。這件事本身不需要新開發。

真正還沒打勾的是進度看板上「SQL 日期查詢改確定性查詢」那一項標成「等你」的原因：**沙盒環境這裡沒有真的 Ollama 跑得起來，這條路線目前只在模擬測試下驗證過 7 種情境全過，還沒在你自己電腦上用真實 Ollama 重新問過確認行為一致。**
