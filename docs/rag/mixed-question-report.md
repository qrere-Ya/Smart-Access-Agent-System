# 🔴 較大項目・第 1 項完成：混合型問題聯合查詢（考勤＋法規）

你選的是 4 個 🔴 較大項目裡的「混合型問題聯合查詢」，已經做完、測完、寫回你的電腦了。

## 這個功能在解決什麼問題

`check_query_route()` 原本只能二選一：一句話要嘛判成 attendance（查考勤資料庫），要嘛判成 law（查法規向量索引）。但像「陳柏豫這個月遲到扣薪上限多少」這種問題，其實同時需要兩邊的資料——考勤資料庫裡陳柏豫實際遲到幾次，跟法規裡扣薪上限怎麼算——二選一分類法只能答對一半。

## 怎麼做的

### 1. `rag_guardrail.py`：新增 mixed 判斷

新增一個「精準優先、寧可漏判也不要誤判」的判斷條件：句子裡要**同時**符合兩個條件才會判成 `mixed`——

1. 出現資料庫裡**真實存在**的員工姓名（用 `rag_sql_engine._get_known_employee_names()` 查，不是隨便講到「員工」兩個字）。
2. 出現法規計算類的詞組（`扣薪`、`上限`、`違法`、`合法`、`罰則`、`賠償`、`罰款`…）。

這個判斷擺在 `check_query_route()` 最前面，比關鍵字快速通道跟語意相似度分類都先跑。

**為什麼故意要求「真實姓名」這麼嚴格：** 2026-09-02 那次修正才好不容易解決「員工遲到是否可以扣除整天薪水」這種純法規問題被誤判成 attendance 的問題，你也已經在真實環境驗證過這個修正有效。這句話裡剛好也有「遲到」「薪水」這些字眼——如果 mixed 判斷只看關鍵字、不要求真實姓名，會讓這句已經驗證修好的句子又被重新誤判成 mixed，等於讓已經驗證過的分類結果倒退。要求「真實姓名」把這種泛稱「員工」的規則類問題排除在外，只留下真的在問「某個人」的混合題型。

**代價：** 像「這個月遲到 5 次扣薪上限多少」這種沒有指名道姓、只問假設情境的混合題型，目前還是判斷不出來、照舊分類走。這是刻意的取捨，優先求不要讓現有分類退步，之後有需要再視情況放寬條件。

### 2. `main_guardrail_rag.py`：新增組合回答邏輯

新增 `_answer_mixed_question(message)`：考勤 SQL 引擎跟法規對話引擎「各自獨立」問一次，互不影響——

- **兩邊都查到**：呼叫一次 LLM，用新的 `_MIXED_ANSWER_PROMPT_ZH` 提示詞把兩段資料整合成一句通順的回答。
- **只有一邊查到**：直接用那一邊的答案，不硬湊。
- **兩邊都查不到**：老實回答「查無符合條件的資料」。
- **LLM 整合這一步本身失敗**（例如 Ollama 逾時）：退而求其次，把兩段原始答案直接接起來回傳（「【考勤資料】...【法規說明】...」），至少不會讓你兩邊資訊都拿不到。

`stream_chat_response()` 跟 `get_chat_response()` 都新增了 `mixed` 分支，接到這支函式，用法跟原本「考勤查無資料、改問法規」那段 fallback 邏輯一致（一次拿完整答案，不逐字流式輸出，因為要先確定兩邊有沒有查到東西才知道最終答案）。

## 測試

這個環境沒有真的 Ollama / bge-m3，沒辦法端對端驗證，所以用這個 session 一路沿用的 stub 測試模式（`sys.modules` 注入假的 scipy / llama_index / database_mgr / rag_sql_engine，但執行真正的 production 程式碼路徑），寫了 20 個測試案例，全部通過：

- `_detect_mixed_question()` 的 true/false case，包含**最重要的一個迴歸測試**：確認「員工遲到是否可以扣除整天薪水」這句已經驗證修好的句子，不會被 mixed 判斷撿回去誤判。
- `check_query_route()`：mixed 判斷有正確擋在關鍵字快速通道跟語意相似度分類之前，且不影響既有分類結果。
- `_answer_mixed_question()`：兩邊都查到／只查到一邊／兩邊都查不到／LLM 整合失敗，四種情境都驗證過。
- `stream_chat_response()` / `get_chat_response()`：mixed 路由確實有接到組合回答邏輯。

## 沒辦法在這裡驗證的部分（老實說）

- 沒有真正的 `bge-m3` 嵌入模型，`check_semantic_guardrail()` 跟語意相似度分類那段完全沒被這次的測試觸碰到（mixed 判斷是純關鍵字＋姓名比對，不依賴嵌入模型，所以這部分可以放心）。
- LLM 整合提示詞的實際輸出品質（會不會真的把兩段資料講得通順、繁體中文、不瞎猜）沒辦法在這裡驗證，需要你在真實 Ollama 環境實際問一次才知道。

## 建議你實際測試的問題

用一個資料庫裡真實存在的員工姓名（例如「陳柏豫」）搭配一個法規計算詞組，例如：

- 「陳柏豫這個月遲到扣薪上限多少」
- 「葉君緯這個月遲到會不會違法扣他薪水」

正常情況應該會看到主控台印出 `[Debug Router] 偵測到「真實員工姓名 + 法規計算詞組」同時出現，判定為 mixed`，回答裡要同時包含陳柏豫實際的考勤數字跟法規扣薪上限的說明。也建議順便重新問一次「員工遲到是否可以扣除整天薪水」，確認這句話還是正確走法規路線（迴歸測試）。
